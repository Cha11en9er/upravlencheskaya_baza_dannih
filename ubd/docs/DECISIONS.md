# Решения по реализации МВП УБД (и почему)

Дата: 2026-11-19. Автор: ZCode (автономная сессия по поручению пользователя).

## 1. Стек

| Выбор | Почему | Альтернатива, почему нет |
|---|---|---|
| **FastAPI 0.165 + Jinja2 + vanilla JS** | Python-стек уже в проекте (парсеры), серверный рендеринг = минимум движущихся частей, работает без сборки фронта | React/Vite — требует npm-цепочку и сборку; для МВП риск выше, ценность та же |
| **SQLAlchemy 2.1 ORM** | Стандарт индустрии, один и тот же код на SQLite и PostgreSQL | Raw SQL — ручная работа с диалектами |
| **SQLite сейчас → PostgreSQL позже** | Пароль postgres неизвестен (scram-sha-256, перебирать пароли нельзя). SQLite = МВП работает сразу | Остаться на SQLite навсегда — нет: мультипользовательская УБД требует PG |
| **JWT в HttpOnly-cookie (PyJWT)** | Серверный рендеринг: cookie проще заголовков Authorization | Session-таблица — избыточно для МВП |
| **pbkdf2_hmac из stdlib (200k итераций)** | Ноль зависимостей, криптостойко; passlib+bcrypt конфликтуют версий на Windows | bcrypt — отдельный C-пакет, выгоды для МВП нет |
| **Vanilla JS + нативный `<dialog>`** | «Проверенные источники»: ноль стороннего фронт-кода, ничего не качается с CDN | htmx — можно добавить позже, прогрессивное улучшение уже заложено |
| **openpyxl** для импорта/экспорта | Уже используется в проекте, читает/пишет xlsx без Excel COM | xlsxwriter — только запись |
| **pytest + httpx2** | Стандарт тестирования; httpx2 нужен, т.к. TestClient в starlette 1.10 deprecated со старым httpx | unittest — меньше удобств |

Версии зафиксированы в `backend/requirements.txt` (точные `==`), установлены
`pip install` из официального PyPI 2026-11-19, воспроизведены в `SETUP.md`.

## 2. Архитектурные решения

- **Серверные калькуляции** (не JS): суммы, отклонения, просрочка, пени, риски
  считаются при каждом сохранении (`services/recalc.py`), хранятся в колонках —
  фильтры и отчёты быстрые, одна истина для всех клиентов. Правила — из ТЗ:
  пени 0,1%/день только для «Подписан»; риск бюджета 🟢≤5% 🟡≤10% 🔴>10%;
  риск просрочки 🟢0 🟡1-5 🔴>5 дней; дата договора = конец тендера + 14 к.д.
- **Деньги — целые рубли** (ТЗ п.9.2: «копейки не учитываются») → Integer,
  нет проблем Decimal на SQLite.
- **ДС обновляет договор**: подписанное ДС переносит сумму/срок в договор
  (`apply_signed_amendment`, берётся последнее подписанное) — ТЗ 3.2.3.4.
- **Права**: per-user JSON `{block: edit|read|none}` + дефолтная матрица по роли
  при создании; проверка фабрикой зависимостей `require_block` в каждом роутере.
  Физическое удаление — только админ и только пустые строки (ТЗ 3.2.3.5, 3.1.3).
- **Оплаты объединены** в одну таблицу (вкладка 3.2.4 + блок 3.3 ТЗ): поле
  kind (Входящий/Исходящий) + contract_id nullable. Упрощение задокументировано
  в MVP_SCOPE.md.
- **recalc_contract считает оплаты SQL-суммой**, а не по `contract.payments`:
  кэшированная коллекция в identity map может быть пустой, если relationship
  загружался до добавления оплат (реальный баг, пойман тестами).
- **Запрет `Request`-параметров без импорта**: с `from __future__ import annotations`
  необозначенный/нерезолвленный тип `request` превращается в обязательный
  query-параметр → 422 (поймано смоук-тестом; в dashboard.py не хватало импорта).
  POST /login сделан без Request (PRG: ошибка через redirect ?error=1).

## 3. Безопасность МВП (осознанные упрощения)

- Пароли: pbkdf2-hmac-sha256, 200 000 итераций, соль 16 байт на пользователя.
- CSRF: SameSite=Lax на cookie + все изменения через POST; полный CSRF-токен —
  следующий спринт (для локального/внутреннего МВП риск низкий).
- SECRET_KEY генерирован `secrets.token_urlsafe(48)`, лежит в `ubd/backend/.env`
  (в репозиторий не попадает), есть `.env.example`.
- Cookie HttpOnly, samesite=Lax, TTL 12 часов (UBD_TOKEN_EXPIRE_HOURS).
